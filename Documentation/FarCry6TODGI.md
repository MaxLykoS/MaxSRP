# Far Cry 6 TOD GI 复现可行性

2026-11-02。评估对象是 MaxSRP 的移动端太阳间接光：静态场景、无破坏、人车只接收 GI、固定太阳轨迹、动态附加灯不产生 GI，云影只影响实时直射。现有人工灯间接光 Lightmap 和天空可见性继续保留。

**复现同类架构可行，精确还原 Dunia 的 GI 实现所需资料不足。** 建议先用 Unity 原生 Light Probe 烘焙建立太阳间接光参考，再实现固定布局、多 TOD 数据和运行时混合。第一阶段不需要运行时 Surfel、静态场景射线更新或完整 APV 移植。难点主要是太阳烘焙输入与单位、空间防漏光、时间插值误差，以及大世界数据量和流送。

| 69 | 天气未完整进入预计算 GI，高云量时降低环境间接光；人工灯独立保存 | 与本项目允许云影不改变太阳 GI 的约束兼容 |
| 70 | 天空大气使用 SH 与 LUT | 这里的 SH 描述不能用来确定 GI Probe 的编码 |
| 111–112 | 镜面反射使用预存几何属性的 Cubemap，并逐面重打光 | 属于反射系统，不是第 69 页的漫反射 TOD GI |
| 144–147 | 附录提供云渲染代码 | 没有提供 GI 烘焙器或 Probe 采样代码 |

11 份 TOD 的备注涉及天空、太阳和月亮。MaxSRP 只保存太阳反弹、继续使用程序天空 IBL，是本项目的适配设计。原文的每日烘焙指制作流程；13 份状态不代表 13 个渲染帧、反弹次数或更新周期。世界分区的 64×64 米 sector 也不能直接当成 GI 常驻范围或官方内存配置。

| 缺少的规格 | 对复现的影响 |

| GI 专项耗时、Probe 总数、CPU/GPU 内存与流送策略 | 原文不能证明我们的中端手机预算，也不能给出准确全图数据量 |

本项目可以复现相同的数据流，结果应称为参考 FC6 的 TOD Probe GI，而非原厂算法的逐项复刻。

## MaxSRP 的光照分工

| 光照分量 | 静态场景 | 人物和车辆 |
| --- | --- | --- |
| 太阳直射及云影 | 现有太阳、大气透射和 CSM | 同左 |
| 太阳间接光 | 新增太阳专用 TOD Probe | 采样同一份太阳 Probe |
| 固定人工灯间接光 | 保留现有 Directional Lightmap | 另烘一次空间 SH 场 |
| 天光 | 保留程序天空 IBL × 表面 SkyVisibility | 需要空间天空可见性数据 |
| 动态附加灯 | 保留实时直射，不新增反弹 | 同左 |

天空可见性控制天空遮挡，不等于天空多次反弹。当前范围继续接受这一近似。太阳数据不包含人工灯、自发光、环境天空或太阳直射，避免与现有路径重复。

运行时数据流可以保持简单：

    固定太阳轨迹和 TOD
        → 找到相邻两份太阳间接光数据
        → 在共同的 Probe 布局中混合
        → 带几何约束地重建空间光照
        → 应用接收面的材质响应
        → 与现有直射、人工反弹和天空合成
        → 雾、天空、公共 TAA、曝光

新系统不需要给静态场景发射运行时 GI 射线，也不需要保存 Surfel 传输链接。它仍然需要空间采样数据；之前删除的 VolumeGI 代码和资产不应恢复或隐式复用。

## 当前工程需要补齐的部分

### 隔离的太阳烘焙入口

[MaxLightmapping.cs](../Assets/MaxRendererPipeline/Runtime/MaxLightmapping.cs) 当前只向原生烘焙器提交 Mixed Point，其他光源使用 InitNoBake，方向光太阳因此不会进入烘焙。[MaxBistroLightmapBaker.cs](../Assets/MaxRendererPipeline/Editor/MaxBistroLightmapBaker.cs) 也会将非人工灯设为 Realtime，并检查太阳不能参与人工光烘焙。不能原样循环调用现有人工灯烘焙器生成 TOD。

应建立独立太阳烘焙场景或副本、LightingSettings、输出目录和 Directional 输入模式；环境设黑、人工灯排除、自发光不参与。原人工 Lightmap、SkyVisibility、材质和正式场景绑定保持不变。取消、失败或关闭工具也必须恢复临时全局状态。

Unity 2022.3 的 [Mixed Baked Indirect](https://docs.unity.cn/2022.3/Documentation/Manual/LightMode-Mixed-BakedIndirect.html) 明确让动态物体通过 Light Probes 接收烘焙间接光，同时实时计算直射；[LightProbes.bakedProbes](https://docs.unity.cn/2022.3/Documentation/ScriptReference/LightProbes-bakedProbes.html) 公开 L2 SH 数据。因此原生 Probe 可以作为离线参考后端，但仍须验证自定义烘焙委托下没有直射污染。优先使用这一分离机制，不先采用完整光照减去直射的做法。

### 太阳大气和 SH 单位

[SunLightData.cs](../Assets/MaxRendererPipeline/Runtime/SunLightData.cs) 将太阳强度定义为大气层外、垂直光束方向的 lux；[Lighting.hlsl](../Assets/MaxRendererPipeline/ShaderLibrary/Realtime/Lighting.hlsl) 在实时直射中另外计算地表大气透射。直接把原始太阳强度交给烘焙器，会使低太阳角等条件下的间接光与现有直射失配。

第一版应明确选择：按每个 TOD 的参考地表太阳颜色和强度烘焙，或烘单位太阳响应再运行时调制。前者容易校准，但同一参考高度近似有高差限制；后者只有在入射强度调制近似空间一致时才能简单缩放。不能在接收点再乘一次 CSM 或太阳透射来替代反射源处的入射光处理。

现有 Lightmap 已校准原生辐照度 E 到 MaxSRP 的转换，但不能直接将该系数套到原生 Probe SH。先保存完整 27 个有符号 float32 系数，校准基函数、余弦卷积、单位和最终材质响应；再比较 L1、L2 与 half 的质量。不得将负的 SH 系数逐个截为零，也不得重复应用接收材质或除以 pi。

### 人车和空间重建

[MaxBakedLighting.hlsl](../Assets/MaxRendererPipeline/ShaderLibrary/Realtime/MaxBakedLighting.hlsl) 在没有 Lightmap 的路径中返回零人工反弹、天空可见性一。太阳 Probe 本身不能补齐这两项，人车需要额外的一次性人工光 SH 和空间天空可见性数据。

同一固定 Probe 布局应服务所有 TOD；每次烘焙后按世界位置或稳定 ID 核对对应关系，不能盲信数组顺序。静态场景仍需筛掉墙内点，并用区域隔离、几何权重或方向距离信息限制插值。单纯提高 SH 阶数不会解决穿墙插值。

## TOD 精度和离线数据

建议先比较 8、11、16 个关键时刻，另外独立烘焙中间时刻作为参考。太阳接近地平线、窄窗进光等变化快的区间再加密；11 是原项目选择，不是普遍充分条件。

如果两份端点数据中的反弹来自不同表面，线性混合可能产生双重渐变，不能恢复中间时刻移动的进光位置。TOD 控制器可以连续运行，光照结果的准确度仍由实际烘焙样本和重建方法决定。首版应先验证线性混合，再根据误差选择更多关键帧或压缩方法，不预设少量 PCA 基底必然足够。

固定太阳轨迹应成为资源版本的一部分，包括方向约定、日期或轨迹参数、每个样本的方向与颜色强度。改变轨迹、几何或显著影响反弹的材质后，相关数据需要重烘。

## 内存估算

以下是本项目设计示例，不是 FC6 官方格式或实测。64×64×32 米按 2 米单元中心布点，对应 16,384 个 Probe；实际布局应稀疏化并随场景调整。假设运行时每点每个状态用 32 字节打包 L1 RGB SH，其中包含布局余量。

太阳时间数据大小为：Probe 数 × TOD 状态数 × 每状态每点字节数。

| TOD 状态数 | 全部太阳状态的逻辑数据量 |
| --- | ---: |
| 8 | 4 MiB |
| 11 | 5.5 MiB |
| 16 | 8 MiB |
| 32 | 16 MiB |
| 512 | 256 MiB |

如果使用原生 27 个 float32 系数作为离线参考，11 个状态的 SH 原始载荷为 18.5625 MiB。该参考格式用于质量校准，不能与上述 GPU 格式混用。先前讨论的 512 档太阳可见性曲线，也不能直接等同于 512 个完整光照状态。

一个只常驻相邻时间状态的 GPU 预算例子如下：

| 资源 | 假设布局 | MiB |
| --- | --- | ---: |
| 两份太阳时间状态 | 每点 32 B | 1 |
| 混合结果 | 每点 32 B，可按实现省略 | 0.5 |
| 固定人工光 SH | 每点 32 B，仅供空间接收 | 0.5 |
| 空间天空可见性 | 每点 4 B | 0.0625 |
| Probe 元数据 | 每点 16 B | 0.25 |
| 防漏光辅助数据 | 示例为每点 8×8 RG16F，含一圈边框后 10×10 | 6.25 |
| 索引和工作空间预留 | 暂定 | 1 |
| 核心逻辑合计 | 不含邻区与流送峰值 | 9.5625 |

这套防漏光格式是候选设计，质量尚需验证，原文没有规定它。若所选格式不能阻止薄墙漏光，应改变重建方法或分辨率，再重算预算。

可以先给该规模新增 GPU 资源设置 16–24 MiB 的筛选预算，但需用边界 Probe、跨块插值和 LOD 依赖、预取及切换峰值检验。直接在现有 Lighting 合成可以省去专用屏幕 GI 纹理；新增 960×540 RGBA16F 单张会另占约 3.96 MiB。CPU 上传副本、原生 SH 数组和统一内存平台的进程实测也要记录。

离线分块烘焙仍需包含会影响结果的周边反射表面和远处太阳遮挡物，不能将区块边界当作空场景。运行时只需加载采样所需的光照和可见性数据块，无需为 GI 保持反射源几何或 Surfel 常驻。

按本表格式，一个同等密度区域的 11 份太阳数据、人工光、天空可见性、元数据和防漏光数据约 12.56 MiB，未压缩且未计跨块重复。100 个同类区域约 1.23 GiB。空间流送控制常驻量，全地图包体仍需依靠稀疏布点、室内外不同密度和经过误差验证的压缩。该数值不能按平面面积直接外推到整张地图，楼层与可活动空间都会改变点数。

## 最小实现与验收顺序

1. 在独立白盒或 TinyBistro 副本中接通一个太阳时刻的原生 Probe 导出，保存完整 L2 参考。保持正式人工 Lightmap 和 SkyVisibility 的文件哈希与绑定不变。
2. 使用黑环境、黑反射材质和可见太阳的 Probe 检查直射污染；用已知反射面验证太阳关闭归零、强度翻倍线性和正确的材质响应。核对大气透射策略及 SH 单位。
3. 烘焙少量 TOD，并独立烘中间时刻，分别观察时间插值与空间插值误差。用完整参考区分烘焙错误、压缩误差和重建漏光。
4. 在静态表面和移动接收体上接入太阳分量，同时补齐人车人工光与天空可见性。太阳间接光不能再乘目标像素的太阳阴影。
5. 覆盖薄墙、暗室、窄窗、跨楼层、低太阳角、快速 TOD 跳转，以及室内外移动路径。数据失效时使用明确的低质量回退，不能读取过期块或把未加载区域永久置黑。
6. 再建立世界分块、邻区依赖、预取和加载优先级。按独立的空间块与时间状态组织资源，保证相邻状态使用相同布局、同一采样点权重和稳定身份。
7. 在目标 Android 和 iPhone 上记录 GI 增量 CPU/GPU 时间、CPU/GPU 常驻、切换峰值、上传带宽与长时间降频结果。33.3 ms 是完整帧预算；先给新增 GI 设约 1 ms 的筛选目标属于项目选择，不是文献性能承诺。

合成遵守 [TemporalAA.md](TemporalAA.md)：使用未曝光线性 HDR，在雾、天空、公共 TAA 与曝光前完成；不增加第二套屏幕 GI 历史。连续时间混合不必逐帧清历史，但加载替换、显著 TOD 跳变或传送应按公共历史生命周期处理。

## 可行性结论

| 目标 | 判断 |
| --- | --- |
| 复现静态世界的多 TOD Probe GI 架构 | 可行，适配当前约束 |
| 复用现有原生烘焙作为离线参考 | 原理可行，需先接通隔离方向光输入并校准 Probe |
| 不恢复旧 VolumeGI，也不实现运行时 Surfel | 可以，新太阳缓存的数据与接收接口独立设计 |
| 按官方讲义精确复制原厂编码与成本 | 资料不足 |
| 主流中端手机 30 FPS、大世界量产 | 值得做样片，取决于重建质量、数据量与真机预算 |

最有价值的第一步是单时刻太阳 Probe 的数值闭环，然后验证少量 TOD 与中间参考的误差。先确定需要保存多少光照和采用什么重建，再投入全地图烘焙、复杂压缩或完整 APV 集成。

本次交付为官方资料下载和设计评估，未修改渲染代码、正式场景或烘焙资产，也未进行新的 GI 烘焙或手机性能测试。
